# 接口规范

适用范围：`admin-api-java17-springboot3` 后端新增接口。

本规范由现有 100 个接口的实际写法归纳而成，用于新代码保持一致。存量接口不强制改造，差异见第 10 节。

---

## 1. 基础约定

| 项 | 值 |
| --- | --- |
| 服务地址 | `http://{host}:1024` |
| 公共前缀 | 无（`server.servlet.context-path` 为 `/`） |
| 数据格式 | JSON，UTF-8 |
| 时间格式 | `yyyy-MM-dd HH:mm:ss`，时区 `GMT+8` |
| 鉴权方式 | 请求头 `Authorization: Bearer {token}` |

---

## 2. 路径规范

### 2.1 结构

```
/{模块}/{动作}
/{模块}/{动作}/{参数}
/{模块}/{操作}/{子对象}
```

层级最多三级。超过三级说明资源划分有问题，应重新设计。

### 2.2 模块命名

- 首字母小写，camelCase，多个单词直接连写。
- 不用下划线、中划线、全大写。
- 用单数名词。

| 正确 | 错误 |
| --- | --- |
| `employee` | `Employee`、`employees`、`emp` |
| `helpDoc` | `help-doc`、`help_doc`、`helpdoc` |
| `changeLog` | `change-log` |

### 2.3 支撑能力前缀

支撑类接口统一以 `/support` 开头：

```
/support/{模块}/{动作}
```

示例：

```
/support/cache/clearAll
/support/file/upload
/support/dict/queryPage
```

`/support` 前缀同时决定 Swagger 分组：带此前缀进「支撑接口」组，否则进「业务接口」组。

### 2.4 动作命名

| 动作 | 用途 | 方法 |
| --- | --- | --- |
| `add` | 新增单条 | POST |
| `update` | 修改单条 | POST |
| `delete` | 删除单条 | POST |
| `batchDelete` | 批量删除 | POST |
| `queryPage` | 分页查询 | POST |
| `list` | 查询全部，不分页 | GET |
| `tree` | 树形结构 | GET |
| `detail` / `get` | 单条详情 | GET |
| 自定义动词 | 业务动作，动词开头 | 按是否写数据 |

自定义动词示例：`getAllEmployeeByDepartmentId`、`updatePassword`、`sendEmailCode`。

不要用 `doXxx`、`handleXxx`、`processXxx` 这类无信息量的动词。

### 2.5 路径参数

命名格式 `{对象名}Id`，camelCase：

```
/role/delete/{roleId}
/helpDoc/getDetail/{helpDocId}
/support/cache/clear/{cacheName}
```

一个接口最多两个路径参数。超过两个改用请求体传参。

---

## 3. HTTP 方法

| 操作 | 方法 |
| --- | --- |
| 查询、详情、树 | GET |
| 新增、修改、删除、批量操作 | POST |

**不使用 PUT、PATCH、DELETE。**

现有 100 个接口中 GET 与 POST 各 50 个，无其他方法。前端请求封装也只区分 GET 与 POST，引入 PUT/DELETE 需要额外改动封装层。

写操作必须用 POST。用 GET 执行删除或状态变更，会被浏览器预取、爬虫、缓存机制误触发。

---

## 4. 请求参数

| 场景 | 规则 |
| --- | --- |
| GET 查询条件 | `@RequestParam`，非必填给默认值 |
| GET 路径参数 | `@PathVariable` |
| POST 请求体 | `@RequestBody` + 表单对象，加 `@Valid` |
| 分页 | 继承 `PageParam` |
| 禁止 | 用 `Map`、`JSONObject` 直接接收请求体 |

分页参数由 `PageParam` 提供：

```java
PageParam {
    Long pageNum;              // 页码，必填
    Long pageSize;             // 每页数量，必填，最大 500
    Boolean searchCount;       // 是否查询总数
    List<SortItem> sortItemList; // 排序字段，最多 10 个
}
```

### 4.1 员工邮箱

- `POST /employee/add`、`POST /employee/update`、`POST /employee/update/center` 的 `email` 为选填，可省略、传 `null` 或空字符串；填写时保留原有邮箱格式校验。
- 编辑员工和个人资料时，空邮箱不参与重复检查；有值时仍执行既有重复检查。要清空已保存的邮箱，传空字符串；省略或传 `null` 沿用 MyBatis-Plus 的非空字段更新规则。
- 无需修改 `sql/postgresql.sql`：`t_employee.email` 已允许空值。开启邮箱验证码登录后，无邮箱账号仍需先配置邮箱才能获取验证码。
- 回归检查：前端 `tests/test_employee_email.cjs`、后端 `admin/src/test/java/net/admin/admin/EmployeeEmailTest.java` 已通过，覆盖空值、格式、新增和编辑；真实连库新增尚未验证。更新后须重新编译并重启后端。

## 5. 响应结构

统一返回 `ResponseDTO<T>`：

| 字段 | 说明 |
| --- | --- |
| `code` | 业务码，成功为 `0` |
| `level` | 提示级别 |
| `msg` | 提示信息 |
| `ok` | 是否成功，`true` / `false` |
| `data` | 业务数据 |
| `dataType` | 数据类型标识 |

写法：

```java
return ResponseDTO.ok();
return ResponseDTO.ok(data);
return ResponseDTO.error(UserErrorCode.PARAM_ERROR);
return ResponseDTO.userErrorParam("具体原因");
```

**成功判定以 `code === 0` 为准。** 前端已按此判断，不用 `ok` 字段做主判据。

分页返回 `ResponseDTO<PageResult<T>>`：

```java
PageResult {
    Long pageNum;
    Long pageSize;
    Long total;
    Long pages;
    List<T> list;
    Boolean emptyFlag;   // 当前页是否为空
}
```

## 6. 权限与审计

### 6.1 权限注解

每个接口必须标注权限点：

```java
@SaCheckPermission("模块:功能:动作")
```

命名三段式，全小写，冒号分隔：

| 段 | 取值 |
| --- | --- |
| 模块 | `system`（业务功能）、`support`（支撑能力） |
| 功能 | 对应模块名，如 `employee`、`cache` |
| 动作 | `add` / `update` / `delete` / `query` / `clear` 等 |

示例：

```
system:employee:add
system:employee:update
system:role:menu:update
support:cache:clear
support:helpDoc:query
```

权限点要和 `t_menu` 里的按钮记录一致，否则前端拿不到按钮权限。

### 6.2 操作日志

写操作加 `@OperateLog`，用于操作审计：

```java
@PostMapping("/clearAll")
@OperateLog
public ResponseDTO<String> clearAll() { ... }
```

查询接口不加。

## 7. Swagger 注解

| 位置 | 注解 |
| --- | --- |
| 类 | `@Tag(name = "业务支撑-缓存管理")` |
| 方法 | `@Operation(summary = "清理全部缓存")` |
| 字段 | `@Schema(description = "员工姓名")` |

缺少注解不影响接口可用，但 Swagger 上会只显示方法名，无法阅读。新增接口一律补齐 `@Tag` 与 `@Operation`。

---

## 8. 完整示例

```java
@RestController
@RequestMapping("/support/cache")
@Tag(name = "业务支撑-缓存管理")
@RequiredArgsConstructor
public class CacheController {

    private final CacheService cacheService;

    @GetMapping("/list")
    @Operation(summary = "查询可清理的业务缓存")
    @SaCheckPermission("support:cache:query")
    public ResponseDTO<List<CacheVO>> list() {
        return ResponseDTO.ok(cacheService.list());
    }

    @PostMapping("/clear/{cacheName}")
    @Operation(summary = "清理单项业务缓存")
    @SaCheckPermission("support:cache:clear")
    @OperateLog
    public ResponseDTO<String> clear(@PathVariable String cacheName) {
        return cacheService.clear(cacheName);
    }
}
```

## 9. 新增接口检查清单

- [ ] Controller 放在 `net.admin` 包下
- [ ] 路径首段为模块名，camelCase，单数
- [ ] 支撑能力路径以 `/support` 开头
- [ ] 写操作用 POST，查询用 GET
- [ ] 路径参数命名 `{对象名}Id`
- [ ] 请求体用 Form 对象，加 `@Valid`
- [ ] 返回 `ResponseDTO<T>`
- [ ] 标注 `@SaCheckPermission`
- [ ] 写操作标注 `@OperateLog`
- [ ] 类上有 `@Tag`，方法上有 `@Operation`
- [ ] 新权限点在 `t_menu` 中有对应按钮记录

## 10. 存量差异

以下是现有代码与本规范不一致的地方，仅记录，不强制改造。

| 差异 | 现状 | 说明 |
| --- | --- | --- |
| 支撑接口前缀 | `dict`、`file`、`helpDoc`、`changeLog` 等未加 `/support`，只有 `cache` 加了 | 导致 Swagger 分组错位，这些模块落在「业务接口」组 |
| 写操作走 GET | `/role/delete/{roleId}`、`/department/delete/{departmentId}`、`/employee/update/disabled/{employeeId}`、`/dict/updateDisabled/{dictId}` | 语义不安全，可被预取或爬虫误触发 |
| 类级路径注解 | 22 个 Controller 中 21 个没有类级 `@RequestMapping`，路径整体写在方法上 | 新增接口按规范使用类级前缀，减少重复 |

改造上述内容会牵动前端接口文件和数据库权限点，需单独排期，不混在业务开发中做。
